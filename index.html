02 / BIOMETRIC
🛡️
Secure Face Recognition with Anti-Spoofing

A full month spent testing every available face recognition approach before finding what actually works. Then building an anti-spoofing layer from scratch because no off-the-shelf solution was good enough. The outcome: a 3-stage production pipeline deployed on AWS EC2 that handles real-world identity verification.

▶ The Full Journey
Phase 1 — One Month in the Library Graveyard. Spent a full month systematically testing every mainstream face recognition library. DeepFace, OpenCV face modules, and the face_recognition library — each tried, evaluated, and discarded. Performance on varied lighting, different angles, and partial occlusion was too inconsistent for production use. None cleared the accuracy bar required.
DeepFace ✗face_recognition ✗OpenCV face module ✗
Phase 2 — Building a Siamese Network from Scratch. Decided to go custom. Designed and trained a Siamese network with contrastive loss — learning to push similar faces together and dissimilar faces apart. Built OpenCV-based data collection scripts to capture personal training data. Rewrote it with triplet loss (anchor / positive / negative pairs) for better metric learning. Results were promising — but still fell short of production-grade accuracy.
Siamese + Contrastive Loss ✗Siamese + Triplet Loss ✗Custom data collection pipeline ✓
Phase 3 — FaceNet Breakthrough. Discovered facenet_pytorch — InceptionResnetV1 pretrained on VGGFace2. Cosine similarity for 1:N identity verification. The accuracy jump was immediate and significant — fast enrollment, reliable matching across lighting and angle variation. This became the identity verification backbone.
FaceNet (InceptionResnetV1) ✓Cosine similarity 1:N ✓VGGFace2 pretrained backbone ✓
Phase 4 — Anti-Spoofing: Built from Scratch. The system could now recognize faces accurately — but it couldn't tell the difference between a real person and a printed photo, a passport-size image, or a face on a phone screen. No off-the-shelf anti-spoof model met the requirements. Collected 10,000 images across 5 people — real faces, digital screen attacks, and printed passport-size photos. Trained an EfficientNet-B0 binary classifier. Integrated with YOLOv11-face into a clean 3-stage pipeline: detect face → check liveness → verify identity. Deployed on AWS EC2 via FastAPI.

🎥
AI Camera Security — Violence Detection

Fine-tuned a spatiotemporal deep learning model on 2,000 real-world CCTV clips to detect fights and violent activity in near real-time. Sliding-window GPU inference at ~20 FPS with a three-tier alert system and downloadable detection logs.

▶ The Full Journey
Phase 1 — Model Selection. Evaluated 2D CNN baselines — ResNet-50 frame-by-frame and MobileNet — but they ignored temporal motion, the core signal of violence. Chose R3D-18 (3D ResNet-18) pretrained on Kinetics-400: it processes (B, 3, 16, 224, 224) clips directly, capturing spatio-temporal patterns that flat CNNs cannot.
2D CNN frame-by-frame ✗R3D-18 spatiotemporal ✓Kinetics-400 pretrained ✓
Phase 2 — Dataset & Training. Used the RWF-2000 dataset — 2,000 CCTV surveillance clips (Fight / NonFight, 1,000 each). Froze the backbone for 3 epochs, then full fine-tune with cosine LR + linear warmup, AdamW, label smoothing, and AMP fp16. Best val accuracy 86.5% at epoch 15 (early stop patience 15).
RWF-2000 · 2K CCTV clips86.5% val accuracyAMP fp16 · AdamW · cosine LR
Phase 3 — Inference Pipeline. Naive per-frame inference on a Streamlit UI caused stuttering and inconsistent predictions. Designed a sliding-window pipeline: a background thread feeds frames into a queue → 16-frame deque buffer → batched GPU forward pass (batch=4) every 8 frames. Achieved stable ~20 FPS GPU throughput. Blind test: 81% accuracy, 0.81 F1.
Naive per-frame → unstable ✗Sliding window (stride 8) ✓81% blind test · 0.81 F1 ✓~20 FPS GPU ✓
Phase 4 — Alert System & UI. Built a three-tier alert system: ✅ SAFE (NonFight), 🟡 FIGHT DETECTED (Fight, low confidence), ⚠️ VIOLENCE DETECTED (Fight, high confidence). Streamlit UI shows live confidence scores, per-clip predictions, and a downloadable CSV detection log.

05 / NL → SQL
💬
Natural-Language Factory Reporting Chatbot

A FastAPI service that lets shop-floor staff ask plain-English questions and get answers straight from a 220+ table garment-manufacturing MySQL database — no SQL knowledge required. Claude picks the relevant tables, writes the query, a guard layer enforces read-only safety, and if the first attempt comes back empty the agent investigates why and retries with real data.

▶ The Full Journey
Phase 1 — A Schema With No Signposts. The production database spans 220+ tables covering orders, fabric/GRN, cutting, bundling, sewing, finishing, washing, QC, and packing — but it's a Laravel app that enforces relationships in application code, not MySQL, so there are almost no declared foreign keys. Handing all 220 tables to an LLM on every question was both too expensive and too noisy — the model had no way to know which columns actually joined. Solved it by writing a relationship-notes document encoding the real join conventions (order_id/order_detail_id/order_part_id chains, cut-plan-to-lay-to-bundle lineage, fabric-roll-to-allocation links) and feeding it into every prompt.
220+ tables, no FKs ✗Dumping full schema per question ✗Hand-authored join-key notes ✓
Phase 2 — Picking the Right Tables. Built a two-stage table-selection layer: a business-glossary of 60+ shop-floor terms ("bundle", "cutting", "wip", "kanban", "GRN") mapped to ordered candidate tables, layered under a keyword/column scorer. Neither alone was enough — a question like "sewing WIP by line for order X" only surfaces the tables whose names or columns literally matched the words, missing siblings the join actually needs. Added a domain-group expansion step that pulls in every table from the same production-stage bucket (cutting/lay, bundling, sewing, etc.) once one member of that group is matched, so multi-table questions get everything they need to join correctly.
Keyword match alone → missed joins ✗60+ term business glossary ✓Domain-group table expansion ✓
Phase 3 — Guarding a Read-Only Agent. The model writes raw SQL against a production database, so safety couldn't be an afterthought. Added a regex guard blocking INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/GRANT/CREATE, enforced SELECT-only execution against a read-only engine, auto-injected a 200-row LIMIT when the model forgot one, and ran everything through SQLAlchemy against a dedicated read-only DB user.
SELECT-only enforcement ✓Forbidden-keyword regex guard ✓Auto LIMIT 200 ✓Read-only DB engine ✓
Phase 4 — When the Answer Comes Back Empty. A join across several tables can return nothing even if only one of them is empty — join elimination silently kills the whole result, and a flat "no data found" response was misleading operators into thinking a stage genuinely had zero activity. Built an empty-result investigator: it checks real row counts on every table used in the failed query, identifies which one is actually empty, pulls glossary-defined fallback tables that do have data, and asks the model to rebuild the query joining through whichever tables actually work — returning both the corrected answer and a note explaining the substitution.
Empty join → looked like "no data" ✗Per-table row-count diagnostics ✓Automatic fallback-table rewrite ✓Transparent substitution notes ✓
Phase 5 — Answers, Not Query Dumps. Raw JSON rows aren't useful to factory floor staff. Added a second Claude pass that explains the SQL result in plain English — leading with the direct number/answer, only surfacing caveats (data gaps, substitute calculations, quality issues) when genuinely important, and never presenting a NULL/empty result as a false zero.
Plain-English summarization ✓NULL ≠ zero handling ✓FastAPI /chat endpoint shipped ✓

07 / PERSONA AI
🪞
Self-Persona LLM — A Fine-Tuned Digital Twin

A LoRA fine-tuned "Meiyarasu K" persona on top of Llama-3.2-3B-Instruct, trained to answer in first person about my own career and projects — grounded strictly in what I actually built, with anti-hallucination practices baked into the data, the training run, and the deployment, not bolted on after the fact.

▶ The Full Journey
Phase 1 — The Real Risk Was Confident Fabrication. A generic chatbot fine-tuned on a resume will happily invent a project, a metric, or a company you never worked at — and say it with total confidence. Designed the whole pipeline around preventing that: LoRA-only updates with the base model frozen, so the network's original world knowledge stays intact and it only learns voice and persona on top, never overwriting facts. Loss was computed strictly on assistant-turn tokens — every system/user token masked with -100 — so the model is trained to reproduce the persona's phrasing on top of facts already sitting in the prompt, never to "predict" new ones.
Full-weight fine-tune → knowledge overwrite risk ✗LoRA-only, base frozen ✓Assistant-token-only loss masking ✓
Phase 2 — A 541-Example Dataset Built From Real Work. Every training record traces back to actual project specifics — the stitch-counting CV pipeline, the NL→SQL factory chatbot, the voice assistant, ANPR, face recognition, and independent projects — hand-authored into the exact raw Llama-3 chat-format (<|start_header_id|> turns) the model would see at inference. The same system prompt, containing the full verified background, is repeated across all 541 records so the persona never drifts from the source facts.
541 hand-built training recordsGrounded in real project dataExact Llama-3 chat template ✓
Phase 3 — Training Across Two GPUs Without Silently Breaking. Launching the script directly instead of via torchrun lets HF Trainer silently fall back to naive DataParallel, which gathers every replica's vocab-sized logits onto GPU 0 and OOMs it. Added a fail-fast guard that raises immediately if multiple GPUs are visible but no distributed launch was detected. Trained in fp16 rather than bf16 since Kaggle's T4s are Turing-generation with no bf16 tensor cores. Combined gradient checkpointing, a held-out validation split, and early stopping on eval_loss so training halts the moment the model starts memorizing instead of generalizing — the exact point where small models start confidently inventing details.
Silent DataParallel fallback → GPU 0 OOM ✗torchrun dual-GPU launch + fail-fast guard ✓fp16 for Turing T4s ✓Early stopping on eval_loss ✓
Phase 4 — Fitting a Live Chat Model on an 8GB Card. Running the 3B base model in bf16 alongside a growing KV cache on an 8GB RTX 5050 left almost no headroom, silently spilling into system RAM via Windows' CUDA sysmem fallback and tanking generation speed. Switched to 4-bit NF4 quantization via bitsandbytes, cutting resident weight size to roughly a third of bf16. Since merging the LoRA adapter would require dequantizing the 4-bit weights first — defeating the memory savings — kept the adapter as a live PeftModel wrapper on top of the quantized base instead. Wrapped it all in a Streamlit chat app with token-by-token streaming, throttled to a fixed UI refresh rate so long replies stream smoothly instead of stuttering on every token.
bf16 + KV cache → RAM spillover on 8GB card ✗4-bit NF4 quantization (bitsandbytes) ✓Live PeftModel adapter, no merge ✓Streamlit streaming chat UI ✓

Zero-Budget GUI Agent — Plain English to Windows Control

Inspired by the GPT 6 Astra computer-use idea, I built my own simplified version: type a task in plain English and the agent looks at the screen and operates the PC like a person would. Built with no paid APIs and no dedicated GPU — a government-issued Ryzen 3 laptop is just the eyes and hands, while a free Kaggle 2×T4 GPU runs the open-source GUI-Owl-1.5-8B model in 4-bit behind a free ngrok tunnel.

▶ The Full Journey
Phase 1 — Zero Budget, Split Architecture. The client laptop (AMD Ryzen 3 7320U, no dedicated GPU) can't run an 8B vision-language model, and paid computer-use APIs were off the table. Split the system in two: the laptop only takes screenshots and executes actions, while a FastAPI server on Kaggle loads GUI-Owl-1.5-8B in 4-bit NF4, sharded across both T4s, exposed to the laptop through a free ngrok tunnel. Loop: screenshot → POST /step → one action returned → executed → repeat.

Phase 2 — Making Clicks Land on Any Screen. Model coordinates and real screen pixels didn't line up across resolutions and DPI-scaled displays, so clicks drifted. Switched the model to a normalized 0–1000 coordinate grid independent of screen size, resized screenshots with smart_resize before inference, made the client DPI-aware, and required every click to carry a short label naming the control so the model re-reads its target before acting. Clicks are also clamped away from screen corners so they can't accidentally trip the failsafe.
Pixel coords drifting ✗0–1000 normalized grid ✓Labeled clicks ✓DPI-aware client ✓
Phase 3 — Taming an 8B Model's Output. The model sometimes wrote "Action:" instead of "ACTION:", which the parser missed — so generation ran on and it hallucinated a whole multi-step plan. Made the action parser case-insensitive and string-aware (so a ")" inside typed code doesn't end the call), added a custom stopping criterion that halts generation the moment one complete action line appears, truncated replies to the first action, and forced a short <think> reasoning block on every step. Both server and client parsers now agree on which action is "the" action.
Hallucinated multi-step plans ✗Stop-on-first-action criterion ✓Case-insensitive, string-aware parser ✓Forced <think> block ✓
Phase 4 — Guardrails Around the Model. Small models type a filename and then click somewhere else, repeat the same click forever, or declare victory too early. Built a scaffolding layer: a submit gate (typed text isn't done until Enter or Save — after two refusals the client presses Enter itself), done() verification (the first done() is challenged once to confirm the result is on screen), loop and repeat protection for no-op and toggling actions, and screen-change detection that waits for the display to settle before the next step. Minimizing the agent's own console keeps its log text from looking like a UI change.
Submit gate ✓done() challenged once ✓Loop & repeat guard ✓Settle-wait + change detection ✓
Phase 5 — Follow-Ups, Logs and a Kill Switch. Added session memory so a follow-up like "same file, replace its content with…" resolves against earlier tasks, plus a mouse-to-corner failsafe and full run logs — raw and marked screenshots with JSONL and text logs — so every executed step can be audited. Result: it created a Python file in a test folder, wrote an add-two-numbers program, saved it and ran it in a separate terminal; and it opened Chrome, picked the correct profile avatar and downloaded VS Code.
